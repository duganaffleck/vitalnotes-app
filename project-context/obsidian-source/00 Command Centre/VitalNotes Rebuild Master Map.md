# VitalNotes Rebuild Master Map

## What VitalNotes Is Now

VitalNotes is a student-facing learning guide for paramedicine.

It helps students understand how learning behaves under the conditions of paramedic training:

- cognitive load
- uncertainty
- pressure
- scenario performance
- OSCE evaluation
- memory and retrieval
- note-making
- reflection
- clinical reasoning
- directive interpretation
- performance under pressure

VitalNotes teaches students how to learn paramedicine, not how to memorize more content.

It is not a generic study skills blog.

It is not a protocol summary.

It is not a motivational site.

It is not an app full of busywork.

It is a guided learning system grounded in paramedic education.

---

## Why We Are Rebuilding

The old VitalNotes material contains strong ideas, but the structure grew outward as sections were developed.

The rebuild will:

- reduce repetition
- sharpen the learning arc
- preserve the strongest explanations
- make the guide easier to navigate
- organize content around student problems
- prepare the material for an app-style interface
- support glossary terms, tool drawers, and cleaner section flow

The goal is not to preserve the old site structure.

The goal is to preserve the strongest thinking and reorganize it into something clearer, smaller, more usable, and more navigable.

## New Content Logic

The new guide should be organized around student problems and learning needs, not only around concepts.

Example:

Student problem:  
"I study, but I blank in scenarios."

Underlying concepts:

- cognitive load
- retrieval
- pressure
- recognition
- access
- working memory

Student-facing sections:

- [[../03 Rebuilt Content/01 Why Learning Feels Hard/Why Studying Feels Productive But Fails Under Pressure]]
- [[../03 Rebuilt Content/04 Build Recall/Retrieval and Spaced Learning]]
- [[../03 Rebuilt Content/04 Build Recall/Clinical Recall Without Trivia]]

This logic should guide all future sections.

Students should be able to recognize the problem before they are asked to understand the concept.

## App Assumption

The app is primarily a reading and navigation interface.

It may include:

- learning path navigation
- section reader
- glossary popups
- tool drawers
- related sections
- previous and next navigation
- problem-based entry
- simple Tools Library

It should not become a heavy interactive app at the beginning.

It should not include, in the first version:

- accounts
- dashboards
- badges
- quizzes
- grading
- simulations
- heavy tracking
- AI-guided reflection
- complex personalization
- Obsidian import pipeline
- Anki integration
- deck management
- automated flashcard generation

The app should render the guide.

It should not reinvent the guide.

- Home page
- Learning Path page

- Build Recall cluster

- [[../03 Rebuilt Content/Tools Library/Directive Meaning Check]]

- [[../03 Rebuilt Content/Tools Library/Clinical Recall Prompt Builder]]
- previous and next navigation
- problem-based entry through [[../03 Rebuilt Content/00 Start Here/Where to Begin]]

Reason for including Build Recall:

- the first slice can test the fuller arc from understanding, to usable notes, to reliable access
- it gives the interface enough content variety to test conceptual, practical, and tool-supported sections
- it allows the app to test three active tool types without becoming tool-heavy
- [[../03 Rebuilt Content/04 Build Recall/Anki for Paramedic Learning]] helps test whether a practical system page can remain guide-like without turning VitalNotes into a flashcard platform

Do not begin app production until the Build Recall architecture verification pass and app-readiness checkpoint are complete.

## Non-Negotiables

- Keep the paramedic context central.
- Keep learning science implicit and practical.
- Avoid generic study advice.
- Avoid bloated explanations.
- Avoid thin explanations.
- Avoid overly polished endings or slogan-like lines.
- Avoid em dashes.
- Avoid productivity-app language.
- Avoid making Anki central.
- Use tools and dropdowns only when they serve a clear function.
- Treat this vault as the control layer.
- Preserve the current learning path unless explicitly changed.
- Keep app planning grounded in real drafted content.
- Do not start app development too early.

---

## Current Working Rule

If a new idea appears, place it in the vault before building around it.

If an idea does not clearly belong in the current content map, park it.

If a feature does not help students read, navigate, understand, use a tool, or continue learning, do not build it yet.

If a section does not solve a real student problem, it needs more work.

If the app becomes more interesting than the learning, it is drifting.
